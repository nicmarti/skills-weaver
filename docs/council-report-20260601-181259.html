LLM Council · Verdict

Outil de Debug & Cohérence pour SkillsWeaver

5 conseillers · peer-review anonyme · synthèse du chairman
La question : Concevoir un outil de debug/analyse de cohérence pour le moteur de JdR D&D 5e SkillsWeaver (Go + Gin/HTMX/SSE + agent DM IA). Vérifier la cohérence à deux niveaux — le squelette (campaign-plan : actes, antagoniste, foreshadows, threads) et le déroulé (journal session par session, NPCs, inventaire, progression) — en interne et l'un vis-à-vis de l'autre. Envisagé comme un onglet/URL web, lisible aussi par Claude Code. Un validation.go existe déjà (validation statique du plan). Les données sont déjà partiellement corrompues par d'anciens bugs (IDs de journal troués, chronologie inversée, session-0 fourre-tout, next_id désynchronisé).

Le verdict du Chairman

✓ Là où le council converge (signal fort)

  • « Cohérence » est un mot-valise dangereux. 4 conseillers sur 5 séparent spontanément trois choses : (1) intégrité des données (déterministe, machine), (2) drift squelette-vs-déroulé (diff mécanique), (3) qualité narrative (jugement → IA/humain). Les fusionner = un outil mou qui fait les trois mal. Ne jamais condenser intégrité et narratif dans un seul score 0-100.
  • L'intégrité d'abord — c'est non négociable. Aucune analyse narrative n'a de sens sur des octets corrompus (garbage in). Le journal troué n'est pas une « aventure incohérente », c'est une base corrompue.
  • La corruption vient du write-path, pas du read-path. Un checker en lecture seule qui retrouve les mêmes trous à chaque exécution est du théâtre. Les bugs sont dans le code qui écrit les entrées (allocation d'ID, routage de session, sync du meta).
  • Architecture : un moteur partagé internal/coherence, plusieurs front-ends. CLI et web ne sont que de fins renderers. Émettre du JSON, puis afficher une page par-dessus — ce qui répond aussi à l'ordre de construction.
  • Le rapport machine (JSON) est quasi gratuit et c'est le vrai canal pour Claude Code. Même struct que l'UI humaine, ?format=json.

⚡ Là où le council s'affronte

Le narratif : jamais, ou plus tard ? Le Contrarian veut le reléguer à « plus tard, voire jamais » (un jouet de recherche). Le Penseur 1ers Principes et l'Expansionniste sont d'accord pour ne pas coder les règles narratives en Go — mais pour une raison opposée : parce que Claude Code / l'IA EST le moteur de cohérence narrative. Résolution : ce n'est pas « jamais » — c'est « pas en Go ». Le Go produit des faits structurés ; le jugement narratif est délégué à l'IA qui consomme le JSON.

CLI-en-CI vs onglet web. Le Contrarian veut un sw-validate exit-code en CI (la régression doit « crier » automatiquement). L'Exécuteur et l'Expansionniste poussent l'onglet web. Pas vraiment un conflit : le moteur partagé sert les deux. Mais le Contrarian gagne sur un point — un onglet que personne n'ouvre est mort : il faut un déclenchement automatique (CI ou post-session), pas seulement une page passive.

Vision vs fondations. L'Expansionniste vend le flywheel d'auto-amélioration du DM et le graphe « YouTube gold ». Les quatre autres disent : magnifique, mais bâtir un DM qui « s'auto-corrige » sur des données mensongères rend le DM plus bête. La vision est juste — l'ordre est faux.

🔍 L'angle mort que seul le peer-review a révélé

Les 5 conseillers ont oublié la même chose : la remédiation. Tous parlent de détecter la corruption et de prévenir la future (write-path), mais les deux aventures existantes sont DÉJÀ corrompues. Sans un outil de réparation/migration (sw-adventure repair / mode --fix), le rapport de cohérence restera rouge en permanence sur tous les saves existants → le signal devient inutile et le concepteur arrête de le lire.

Corollaire également manqué : quelle source fait foi quand deux sources se contredisent ? (journal-meta vs fichiers de session ; les deux aventures divergent sur categories[] et la contiguïté des IDs). Impossible de valider contre un schéma qu'on n'a pas gelé et dont on n'a pas désigné l'autorité.

La recommandation

Construire un seul moteur partagé internal/coherence avec trois couches nettement nommées et non fusionnées :

  • Couche 1 — Intégrité (déterministe, Go) : porter les corruptions réelles en checks (checkJournalIDGaps, checkChronoOrder, checkNextIDSync, checkEmptyCategories, session-0 fourre-tout). C'est le ROI le plus élevé et c'est testable contre les données réelles dès lundi.
  • Couche 2 — Drift squelette↔déroulé (diff mécanique, Go) : réutiliser ValidateCampaignPlan() + croiser foreshadows plantés/résolus, threads actifs/abandonnés, NPCs du plan vs npcs-generated.json, sessions cibles des actes vs sessions jouées.
  • Couche 3 — Qualité narrative (PAS en Go) : le moteur émet du JSON ; Claude Code/l'agent juge. Optionnellement réinjecté dans le briefing world-keeper plus tard (la vision de l'Expansionniste — phase tardive).

Émettre une struct Report{Skeleton, DataIntegrity, Drift, Score-PAR-COUCHE} avec Finding{Severity, Rule, Message, Context}. Exposer (a) une route web GET /play/:slug/coherence (partial HTMX cloné de /info) + ?format=json pour Claude Code, et (b) un binaire fin sw-validate exit-code pour la CI. Mais d'abord, en parallèle de la couche 1, livrer un sw-adventure repair qui re-home les orphelins de session-0, resynchronise next_id et fige le schéma — sinon l'outil ne fait que peindre joliment la corruption.

Ce qu'on ne fait PAS maintenant : graphe de foreshadows, SSE, flywheel agent, score global unique, règles narratives en Go.

La seule chose à faire en premier

Créer internal/coherence/integrity.go avec checkJournalIDGaps(advDir) []Finding, et écrire le test qui assure qu'il retrouve les IDs manquants connus (81, 104, 106, 127) sur le-voyageur-de-tuncmor. Test vert = la fondation déterministe tient. Tout le reste (drift, web, JSON, repair) se branche dessus ensuite.

Réponses complètes des conseillers

Le Contrarian  — C'est un problème de writes, pas d'outil

Tu traites ça comme un problème d'outillage alors que les données prouvent que c'est un problème de writes. IDs fragmentés, chronologie inversée, session-0 fourre-tout, next_id désynchronisé. Un analyseur de cohérence ne corrige rien de tout ça — il génère juste un plus joli rapport de la corruption que ton code continue de produire. Construis le dashboard read-only et tu passeras le mois prochain à fixer une magnifique timeline de déchets. Fixe le write-path du journal (allocation d'ID atomique, routage de session, sync du meta) D'ABORD, ou l'outil mesure du bruit.

Deuxième faille fatale : la « cohérence » entre squelette et déroulé n'est pas calculable, et tu fais semblant que si. Les règles d'intégrité (trous d'ID, liens foreshadow orphelins) sont déterministes — ok, automatise-les. Mais « est-ce que l'arc de l'antagoniste a vraiment avancé cette session ? » exige de lire la prose des champs Content et de juger l'intention narrative. Ton score validation.go (0-100) va confondre « aucun ID manquant » avec « l'histoire a du sens », et tu feras confiance à un chiffre vert qui ne veut rien dire. Ne fusionne JAMAIS intégrité et narratif en un seul score.

Troisième : qui consomme ça, et quand ? Un onglet de debug que personne n'ouvre en cours de session est un poids mort. Si c'est pour le concepteur, il doit tourner automatiquement et hurler à la régression — sinon la corruption revient en silence, exactement comme elle l'a déjà fait.

Questions que tu évites : Tes deux aventures sont en désaccord sur categories[] et la contiguïté des IDs. Laquelle est « correcte » ? Tu ne peux pas valider contre un schéma que tu n'as pas gelé. Quel est le coût des faux positifs ? Un analyseur qui signale 40 « incohérences narratives » par session est pire que rien. Pourquoi une UI graphe/timeline avant un seul test CI qui échoue ?

Verdict : plus petite chose viable — un CLI sw-validate sur un schéma gelé, lancé en CI, intégrité-seule, piloté par exit-code. La « cohérence » narrative est un jouet de recherche ; livre-la en dernier, si jamais.

Le Penseur Premiers Principes  — Deux problèmes de formes opposées

Tu confonds deux problèmes qui ont des formes opposées, et le cadrage le cache.

« Cohérence » suppose que les données sont fiables et que tu vérifies si l'histoire tient. Mais tu as déjà trouvé que le journal est structurellement cassé : trous, chronologie inversée, dumping en session-0, next_id désynchronisé, categories vides. Ce n'est pas une aventure incohérente. C'est une base de données corrompue. Aucune analyse narrative ne signifie quoi que ce soit par-dessus de mauvais octets — tu noterais la prose d'un document dont les pages sont dans le désordre.

Donc dépouille : tu as deux primitives distinctes, et elles sont en couches.

1. Intégrité (les données sont-elles bien formées et canoniques ?) — déterministe, mécanique, doit passer avant que quoi que ce soit d'autre ne tourne. C'est le vrai problème urgent, et il est causé par les writers, pas les readers. Un checker read-only qui trouve des trous à chaque fois est du théâtre ; les bugs sont dans le code qui écrit. La source unique de vérité est le fix. Rends l'allocation d'ID, le routage de session et l'ordre corrects-par-construction au write-path. Alors le check d'intégrité devient un garde-fou de régression, pas un pansement.

2. Cohérence (l'histoire bien formée a-t-elle du sens ?) — n'a de sens qu'au-dessus d'une couche d'intégrité qui passe, et intrinsèquement floue/de jugement — c'est là que l'LLM/Claude Code intervient, pas un moteur de règles Go.

Réponse à « le check de cohérence est-il la bonne primitive ? » : Non, pas en premier. Construis l'intégrité comme couche déterministe internal/coherence (renomme : integrity) + le fix du write-path. Émets un rapport JSON (Claude est ton vrai moteur de cohérence — ne hardcode pas les règles narratives en Go). L'onglet web est un viewer, phase 3.

Mauvaise question : « comment détecter l'incohérence ? » Bonne question : « pourquoi mes données me mentent-elles, et qu'est-ce qui rend une source autoritaire ? »

L'Expansionniste  — Pas un linter : le moteur qui rend le DM plus malin

Construis le checker de cohérence comme un package partagé internal/coherence d'abord — c'est le point de levier. CLI et web ne sont que de fins renderers. Mais voici ce que tout le monde va sous-estimer : ce n'est pas un outil de debug, c'est un moteur de qualité narrative et un flywheel d'entraînement du DM IA.

Le vrai prix : chaque règle de cohérence que tu écris (foreshadow abandonné, thread délaissé, importance de NPC jamais payée, stagnation de pacing) devient un signal de feedback réinjecté dans l'agent sw-dm. Émets le rapport JSON, puis nourris les violations dans le briefing world-keeper à start_session. Maintenant le DM s'auto-corrige en cours de campagne. Tu n'analyses plus la cohérence — tu boucles la boucle pour que l'IA s'améliore plus elle joue. C'est un moat qu'aucun autre projet d'IA-DM n'a.

Plus gros coups cachés ici :

  • Le graphe de foreshadows est de l'or YouTube. Un graphe de dépendances « fusil de Tchekhov » en live — planté vs tiré — est hypnotique à la caméra et explique la sophistication de ton moteur instantanément. Construis la visualisation pour être screenshotée, pas juste déboguée.
  • Le Score de Cohérence dans le temps = le battement de cœur de ta campagne. Trace-le par session. C'est un dashboard d'arc narratif que créateurs et joueurs veulent.
  • Le diff squelette-vs-déroulé est un produit réutilisable. « Voilà ce que tu avais prévu, voilà ce qui a émergé. »
  • Règles comme données, pas comme code. Rends les règles déclaratives (JSON/YAML) pour que Claude Code puisse écrire de nouvelles règles par l'exemple.

Phase 1 : package partagé + rapport JSON + 5 règles. Phase 2 : réinjection dans la boucle agent. Phase 3 : le graphe que tout le monde screenshote. Ne construis pas un linter. Construis la chose qui rend le DM plus malin à chaque session.

L'Outsider  — « Cohérent » fait trop de travail

Voici ce sur quoi un outsider trébuche :

« Cohérent » fait trop de travail. Tu empiles trois contrôles sans rapport sous un seul mot : (1) intégrité des données — fichiers corrompus, IDs manquants, événements dans le désordre ; (2) drift plan-vs-réalité — l'histoire jouée a-t-elle suivi l'histoire planifiée ; (3) qualité narrative — l'histoire a-t-elle du sens / tient-elle. Ce sont des problèmes radicalement différents. (1) est un linter déterministe — une machine dit oui/non. (2) est un diff — assez mécanique aussi. (3) est un jugement qui exige une IA ou un humain. Les mélanger = un outil mou qui fait les trois mal. Nomme-les séparément.

Qui ouvre ça, et quand ? Non dit. Un créateur solo qui débugge du code ? Alors c'est un outil de dev qu'on regarde après une session. Un Maître du Jeu qui prépare la semaine prochaine ? Audience différente, surface différente. Tu ne peux pas concevoir la visualisation avant d'avoir répondu à ça, et tu n'as pas répondu.

Le but humain-visuel et le but IA-lisible ne sont PAS le même outil. L'IA veut des faits structurés (JSON : « l'événement 47 n'a pas d'ID », « le thread X n'a jamais été résolu »). Un humain veut une forme saisissable d'un coup d'œil — une timeline, des drapeaux rouges, « l'acte 2 n'est jamais arrivé ». Le moteur d'analyse est partagé ; les renderers de sortie diffèrent. Construis le moteur une fois, émets du JSON, puis affiche une page par-dessus. Ça répond aussi à ton ordre de construction.

Ordre : fixe l'intégrité d'abord. Tu ne peux littéralement pas juger « l'histoire a-t-elle été cohérente » sur des données corrompues — garbage in. Donc : (1) linter d'intégrité + meilleur logging (même fix — ta corruption venait d'écritures bâclées), (2) rapport JSON, (3) checks de drift/qualité, (4) l'onglet web en dernier.

Ne construis pas le joli onglet en premier. Il ne fera que visualiser des données cassées.

L'Exécuteur  — Ce que tu codes lundi matin  ★ jugée la plus forte

Construis internal/coherence/ comme package partagé — pas un nouveau binaire, pas web-first. L'onglet web et tout futur sw-debug appellent dedans. Un package, plusieurs front-ends.

Lundi matin, dans l'ordre :

1. internal/coherence/report.go — définir le type de sortie, en réutilisant ta forme existante :

type Report struct {
    Skeleton      adventure.ValidationResult // existe déjà
    DataIntegrity []Finding
    Flow          []Finding
    OverallScore  int
}
type Finding struct {
    Severity string // "error"|"warning"|"info"
    Rule     string // "journal.id_gaps"
    Message  string
    Context  map[string]any
}

2. internal/coherence/analyze.go — func Analyze(advDir string) (*Report, error). Charge journal-meta + sessions, appelle l'existant ValidateCampaignPlan(), fourre le résultat dans Report.Skeleton.

3. internal/coherence/integrity.go — porte la corruption que tu as DÉJÀ trouvée en checks déterministes : checkJournalIDGaps, checkChronoOrder, checkNextIDSync, checkEmptyCategories. Ce sont de vrais bugs aux signatures connues — écris-les en premier, ROI maximal.

4. Câble une route Gin : GET /play/:slug/coherence renvoyant un partial HTMX qui itère sur les Findings dans un <table>. Copie le handler /info verbatim et change le corps.

À zapper pour l'instant : règles narratives/gameplay, SSE, visualisations, extension de logs. Livre intégrité + squelette cette semaine.

Pour (d) le JSON machine : gratuit — ajoute ?format=json à la même route, c.JSON(200, report). Même struct, zéro travail en plus. C'est ton feed Claude Code.

Premier pas que tu peux littéralement faire maintenant : crée integrity.go avec checkJournalIDGaps. Tu sais déjà qu'il trouve 81,104,106,127. Écris cette fonction, assure contre l'aventure réelle, test vert, fini.

Faits saillants du peer-review

Les 5 relectures anonymes (consensus + angle mort collectif)

Consensus unanime (5/5) : la réponse de l'Exécuteur est jugée la plus forte — seule à transformer le design en code livrable lundi (structs concrètes, réutilisation de ValidateCampaignPlan(), corruptions réelles portées en checks, handler /info cloné, JSON gratuit, premier test vert contre données réelles), tout en absorbant l'insight juste des autres (intégrité d'abord, moteur partagé, JSON-puis-render).

Plus gros angle mort (5/5) : la réponse de l'Expansionniste — elle romance le flywheel narratif et le graphe « YouTube gold » en ignorant que les données sont déjà corrompues. Nourrir le briefing du DM avec des violations bruitées rendrait le DM plus bête. La vision est juste, l'ordre est faux.

Ce que les 5 ont tous manqué (relevé par les 5 relecteurs) : la remédiation / migration des données déjà corrompues. Tous détectent et préviennent, aucun ne répare. Sans un sw-adventure repair / mode --fix (re-homing des orphelins de session-0, resync de next_id), le rapport reste rouge à vie sur les saves existants. Corollaire : désigner la source autoritaire quand journal-meta et fichiers de session se contredisent, et geler le schéma avant de valider contre lui.
