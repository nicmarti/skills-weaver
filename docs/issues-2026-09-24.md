## Problème 1 — Timeout de la génération du plan de campagne (bloquant, à corriger)

**Symptôme**

```
Warning: wizard campaign plan generation failed: API call failed: llm: request deadline exceeded (kind=timeout status=0)
```

L'aventure était tout de même créée et jouable, **sans** `campaign-plan.json`
et **sans** PNJ pré-générés (la génération de PNJ est dans le `else` du succès).
Le briefing narratif du DM (`CAMPAIGN CONTEXT` au `start_session`) est donc absent.

**Cause racine (diagnostic complet après investigation)**

1. `generateCampaignPlanWithBrief` utilisait `llm.Complete()` : un appel
   **non-streaming** qui attend la réponse entière avant de rendre la main.
2. La requête demandait jusqu'à 8192 tokens de JSON structuré (3 actes, PNJ,
   lieux, foreshadows) en mode JSON strict (`RequireParameters: true`).
3. Sonnet 5 est un modèle de raisonnement : les tokens de raisonnement
   s'ajoutent à la sortie ; la génération mesurée prend ~2 min 40 s
   (158 s, dont 90 s avant le premier delta).
4. **Cause déterminante (mesurée)** : le client HTTP partagé de
   `internal/llm` imposait `http.Client.Timeout = 60 s` — or en Go ce cap
   couvre **aussi la lecture du body**, y compris en streaming : toute
   génération de plus de 60 s était tuée net (la requête coupait
   exactement à 1:00:27 lors du benchmark). Le contexte de 120 s côté
   handler n'était jamais atteint.
5. Deux causes secondaires corrigées au passage :
   - `MaxCompletionTokens = 8192` incluait le raisonnement : Sonnet 5 a
     produit une réponse **vide** avec `finish_reason=length` (les 8192
     tokens consommés par le thinking). Relevé à 16384.
   - Variabilité du modèle : `supporting_characters` parfois émis comme
     des strings au lieu d'objets → parse JSON en échec. Tolérance ajoutée
     (`adventure.Character.UnmarshalJSON` accepte une string isolée,
     interprétée comme nom).

**Correctif implémenté**

- `internal/llm/openrouter.go` : le client HTTP par défaut n'a plus de cap
  total (`Timeout = 0`) ; la protection anti-provider-bloqué devient un
  `Transport.ResponseHeaderTimeout = 60 s` (les headers doivent arriver en
  60 s, mais le body peut streamer aussi longtemps que le contexte
  l'autorise). Tous les appelants de `Complete` passent déjà un ctx borné.
- Génération passée en **streaming** (`llm.Stream()` via
  `internal/campaign.Generate`), contexte **10 minutes** (décision révisée
  le 24/09/2026 : initialement 5 min max, relevé à 10 min pour garantir un
  plan complet avec Opus 5.5 à effort medium).
- `MaxCompletionTokens` relevé à 32768 pour couvrir raisonnement + JSON.
- **Rôle Campaign = Opus 5.5** (`DefaultModelCampaign = anthropic/claude-opus-5.5`,
  décision du 24/09/2026) avec **`reasoning.effort = "medium"`**
  (`campaign.DefaultReasoningEffort`) : à l'effort fournisseur par défaut,
  Opus 5.5 dépasse les 5 minutes ; à medium il tient largement. Le contrôle
  `ReasoningEffort` est exposé dans `llm.Request` et par le flag
  `--reasoning` de `sw-bench-campaign`.
- **Trame foreshadows explicite** dans le prompt (décision du 24/09/2026) :
  le template `"active": []` ne donnait aucune structure, les modèles
  improvisaient (ids numériques, champs ad-hoc). Le prompt exige désormais
  `id, description, introduced_session, introduced_act, expected_payoff_act,
  linked_element` (ids `fsh_001`, `fsh_002`...) ; champs ajoutés à
  `adventure.ForeshadowLinked` (les anciens tags restent lus pour les plans
  déjà sauvegardés).
- **Génération avant sauvegarde** : le plan est généré et validé en mémoire ;
  l'aventure n'est écrite sur disque que si le plan est valide.
- **Erreur bloquante** : si le plan de campagne **ou** la génération des PNJ
  échoue, la création échoue — HTTP 500/502/503 avec message affiché dans
  l'interface (wizard : JSON `error` affiché par `failOverlay` ; formulaire
  classique : page d'accueil re-rendue avec bandeau d'erreur), avec rollback
  du répertoire d'aventure si un échec survient après sauvegarde.
- Code partagé extrait dans `internal/campaign` (prompt + stream + parse),
  réutilisé par le web et par l'outil de benchmark `sw-bench-campaign`
  (un seul modèle par invocation, format OpenRouter complet `provider/model`).

**Prototype multi-tour (24/09/2026, benchmarké puis RETIRÉ — décision finale : one-shot Opus 5.5 medium)**

Question posée : pourrait-on construire le plan par une conversation guidée
(tours = fondations, actes, antagoniste, PNJ ×2, lieux, présages) avec
sous-schéma par tour, écho du plan accumulé et cache de prompt
(`cache_control` éphémère, fenêtre de 4 breakpoints) ?

Le prototype (`internal/campaign/multiturn.go`, `GenerateMultiTurn`, flag
`--strategy multi-turn` du bench) a été implémenté, mesuré, puis **retiré du
code** après la décision de garder la génération one-shot. Les résultats du
benchmark restent documentés ci-dessous pour mémoire.

**Comparaison mesurée — Opus 5.5, effort medium, même thème :**

| Stratégie | Total | TTFB | Tokens entrée | Tokens sortie | Cachés | Coût | Score |
|---|---|---|---|---|---|---|---|
| oneshot | **141,8 s** | 52,1 s | 31 617 | 12 440 | 0 | **$0,38** | 100/100 |
| multi-turn (7 tours) | 341,8 s | 17,5 s | 371 455 | 27 274 | 284 956 | $1,03 | 100/100 |

**Enseignements :**
- Le **cache fonctionne** : les tours 2-7 lisent 26K→72K tokens du cache
  (facturés ~10 %). La mécanique `cache_control` est validée côté boundary
  `llm` (reusable ailleurs).
- Mais le multi-tour **perd sur les deux tableaux** avec ce workload :
  - **Temps** : 7 round-trips sérialisés (TTFB 8-27 s chacun) + raisonnement
    ré-engagé à chaque tour + sorties verbeuses par étape (jusqu'à 7 355
    tokens de sortie pour le tour antagoniste).
  - **Coût** : l'historique rejoué fait gonfler l'entrée à 371K tokens
    cumulés (12× le one-shot) ; même à 10 % pour la partie cachée, la sortie
    totale (27K tokens, plus verbeuse que le gabarit one-shot) domine.
- Les avantages réels constatés : progression par étapes (TTFB 17 s puis
  tours visibles), retry par tour à bas coût (testé unitairement), et score
  égal (100/100, trame foreshadows respectée).

**Conclusion (décision actée : oneshot conservé)** : pour une génération
one-shot d'un artefact structuré, le prompt monolithique avec effort de
raisonnement contraint reste supérieur. Le multi-tour redeviendrait pertinent
si le wizard devenait interactif (l'utilisateur validerait chaque étape) —
auquel cas découper l'écho du plan au strict nécessaire par tour et
contraindre la verbosité (json_schema strict) seront les leviers clés.

Seule la mécanique `cache_control` de la boundary `llm` (`Message.CacheBreakpoint`,
`CachedUserMessage`, tests wire-format) est conservée : validée en conditions
réelles, elle reste réutilisable pour toute conversation multi-appels
(ex. boucle DM).

## Problème 2 — Google Imagen 404 (non bloquant, fallback fal.ai)

**Symptôme**

```
[image] primary provider (Google Imagen) failed: API error (status 404): {
  "error": { "code": 404,
    "message": "models/imagen-4.0-generate-001 is not found for API version v1beta, or is not supported for predict. ...",
    "status": "NOT_FOUND" }
}
[image] falling back to secondary provider (fal.ai)
[image] fallback provider (fal.ai) succeeded
```

**Cause racine**

`internal/image/google.go:15` hardcode `imagen-4.0-generate-001:predict` sur
l'API Gemini Developer (`generativelanguage.googleapis.com/v1beta`).
Vérification faite le 24/09/2026 via `ListModels` avec la `GEMINI_API_KEY`
du projet : **aucun modèle `imagen-*` n'est disponible** (61 modèles, zéro
Imagen). Les modèles d'image réellement disponibles passent par
`generateContent` : `gemini-2.5-flash-image` (Nano Banana),
`nano-banana-pro-preview`, `gemini-3-pro-image`, `gemini-3.1-flash-image`.

Conséquence : chaque génération d'image échoue d'abord sur Google (404,
~1 s perdue) puis retombe sur fal.ai — fonctionnel mais consomme des crédits
fal inutilement et ralentit chaque image.

**Correctif envisagé (à implémenter séparément)**

Réécrire `GoogleGenerator` pour utiliser un modèle d'image disponible via
`generateContent` (p.ex. `gemini-2.5-flash-image`), ou inverser la priorité
des providers dans `NewGeneratorAuto` (`internal/image/image.go:123`).

**Statut : non traité dans ce changement** — la correction se concentrera
d'abord sur le Problème 1 (wizard campaign plan).
